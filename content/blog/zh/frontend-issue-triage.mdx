线上问题和本地调试是两回事：本地能断点、能改代码、能重跑；线上只有少量信息、有业务压力，还常常无法复现。定位能力的高低，就体现在“用最少的信息，最快缩小范围”。

## 三条总原则

**先止血，后根因。** 影响仍在扩大时，优先回滚、降级、切开关，把问题压住再慢慢查。根因分析是为了不再复发，不是止损的前提。

**控制变量，二分缩小。** 从“问题边界”入手：是全部用户还是部分用户？是所有页面还是单个路由？是特定机型、网络或版本吗？每问一次，范围就砍掉一半。

**用数据说话。** 每个假设都要有可验证的证据：一次抓包、一段堆栈、一条监控曲线。不要靠猜——猜错的成本是一次错误的“修复”。

## 信息采集：别急着看代码

### 用户反馈要素清单

- 发生时间（越精确越好，方便对齐日志）
- 环境：浏览器与版本、系统、网络、浏览器内还是 App 内嵌
- 账号与租户：是否新用户、特定权限、特定配置
- 操作路径：从哪个入口进来，依次点了什么
- 截图或录屏，有 Console 报错更好（远程指导用户按 F12 也能救急）
- 是否稳定复现，换环境、换账号是否依旧

### 错误监控与 Source Map

页面级兜底可以先接上全局错误监听：

```ts
window.addEventListener("error", (event) => {
  report({
    type: "error",
    message: event.message,
    source: event.filename,
    line: event.lineno,
    column: event.colno,
    stack: event.error?.stack,
  });
});

window.addEventListener("unhandledrejection", (event) => {
  report({ type: "unhandledrejection", reason: String(event.reason) });
});
```

线上代码经过压缩混淆，堆栈必须靠 Source Map 还原才可读。要点：

- Source Map 上传到错误监控平台，不要作为静态资源公开发布
- 留意框架包装后的堆栈：异步边界、事件回调中的错误容易丢失业务上下文
- 上报附带版本号，方便按发布批次聚合分析

## 工具箱速查

| 工具 / 面板 | 主要用途 |
| --- | --- |
| Network | 请求瀑布、状态码、失败类型；限速模拟弱网；重放请求 |
| Performance | 录制主线程活动，定位长任务、强制同步布局、频繁 GC |
| Memory | 堆快照对比找泄漏；分配时间线观察对象增长 |
| Application | 缓存、Storage、Service Worker、Cookie 是否异常 |
| PerformanceObserver | 线上无 DevTools 时采集长任务、资源与自定义指标 |
| 版本比对 | 问题时间点与发布记录对齐，最高效的定位手段之一 |

线上采长任务可以这样写：

```ts
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration < 100) continue;
    report({
      type: "longtask",
      start: entry.startTime,
      duration: entry.duration,
    });
  }
});

observer.observe({ entryTypes: ["longtask"] });
```

再配合 Web Vitals（LCP / INP / CLS）判断影响面：指标在哪个版本开始劣化，问题往往就出在哪次发布。

## 五类高频问题的定位路径

### 白屏

症状：页面骨架出现，内容完全不渲染，或整页空白。

- 怀疑顺序：静态资源 404 或加载失败 → JS 执行报错（入口 chunk 挂了）→ 路由或权限守卫拦截 → 渲染异常被兜底捕获
- 验证手段：Network 看 HTML 与入口 JS 的状态码；Console 看**第一条**报错而不是最后一条；对比正常与异常环境的构建版本

### 接口异常

症状：数据不展示、频繁报错提示、部分功能不可用。

- 怀疑顺序：状态码（4xx 多为鉴权或参数，5xx 看服务端）→ 超时与弱网 → 跨域与协议（https 跳转、混合内容）→ 响应格式变化（字段改名、类型变化、空值语义）
- 验证手段：Network 复现请求看原始响应；用 curl 绕过前端直接调；把前端发出的参数与网关日志比对

### 交互无响应

症状：点击没反应、弹窗打不开、按钮“失灵”。

- 怀疑顺序：JS 报错中断了事件处理 → 事件绑定丢失（列表重渲染、事件委托失效）→ 主线程被长任务阻塞 → 层级或遮罩挡住了点击
- 验证手段：Elements 面板看事件监听器；Performance 看点击时刻有没有长任务；用 `document.elementFromPoint` 确认点击最终落在哪个元素上

### 卡顿

症状：滚动掉帧、输入延迟、动画一顿一顿。

- 怀疑顺序：长任务（大数组计算、同步渲染）→ 高频事件未节流 → 大量 DOM 变更引发重排重绘 → 内存压力导致 GC 抖动
- 验证手段：Performance 录制火焰图，把 Long Task 与用户操作时间对齐；用实时帧率悬浮窗快速感知

### 内存泄漏

症状：越用越卡，刷新后恢复。

- 怀疑顺序：定时器与监听器未清理 → 全局缓存无限增长 → 闭包引用大对象 → 三方库实例未销毁（图表、编辑器、3D 场景）
- 验证手段：Memory 面板连续抓两个堆快照对比“保留对象”；Performance 勾选内存观察堆曲线是否锯齿向上

## 小结

定位的本质是缩小范围：先收集足够的信息，再用控制变量的方式逼近边界，最后用数据验证假设。工具与清单都是为这个循环服务的——常备在手，遇事不慌。
